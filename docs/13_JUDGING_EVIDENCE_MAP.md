# 13 심사 기준과 실행 근거

v0.3 구현 문서 · 2026-10-09

## 1. 평가 관점

[공식 행사 안내](https://luma.com/f7h7onav)의 문제 정의, AI 판단, 작동하는 결과물, 검증·개선, 도입 가능성, Codex 활용 과정을 기능과 실제 근거에 연결한다. 아래는 팀의 증거 설계이며 배점이나 추가 공식 제출 요건을 정한 것이 아니다.

## 2. 기능과 증거 대응

| 평가 관점 | 보여줄 내용 | 기능·담당 | 실제 근거 | 현재 |
|---|---|---|---|---|
| 문제와 필요 | 점검 범위·남은 일·책임자 확인의 어려움 | 공통 | 원문 사례, 관찰/인터뷰 또는 합성 시나리오 표시 | 가설 |
| AI 판단 | 조회 근거를 사용한 질문·답변 후 작업 후보 | F1 재곤 | L1a/L1b run, 실제 도구 결과·Request·draft·Action 연결 | NOT_RUN |
| 실행 가능한 제품 | 승인된 작업이 인수·결과·해결까지 이어짐 | F1~F4 각각 | T8 사건 ID·역할별 명령·DB 재조회·영상 | NOT_RUN |
| 실패 대응 | stale 결과·반려·중복·worker 복구 보존 | 각 기능 | T1~T12와 실제 실패/수정/재시험 기록 | NOT_RUN |
| 도입 가능성 | 한 라인의 교대 확인 부담을 줄일 가설 | 공동 | 파일럿 대상·기존 절차·측정 계획·반례 | 미검증 가설 |
| Codex 활용 | 기능별 지시와 사람의 검토·통합 | 각 기능 | CODEX_WORKLOG의 실제 지시·diff·시험·검토 | 문서 작업만 기록 가능 |

## 3. 주장 범위

| 말하려는 주장 | 필요한 최소 근거 | 근거가 부족할 때의 표현 |
|---|---|---|
| AI가 모호한 범위를 확인한다 | L1a의 실제 검색과 Request | 확인 질문을 만들도록 설계했다 |
| AI가 입력에 따라 질문 여부를 달리한다 | 충분한 입력 대조 L4·표현 변형과 실제 결과 | 모호한 대표 사례 한 건에서 질문 생성을 확인했다 |
| 중복 작업을 막는다 | L2와 서버 unique/재전송 시험 | 서버 중복 방지 계약을 정의했다 |
| 교대 책임이 이어진다 | 정상 ACK와 stale/reACK의 owner·assignee 기록 | 책임 이전을 설계했다 |
| 장애에도 기록이 남는다 | 모델 실패와 worker 종료/재시작을 각각 실행 | 영속 저장·복구를 설계했다 |
| 업무 시간이나 누락이 줄었다 | 같은 조건의 전후 측정·표본·한계 | 향후 측정할 가치 가설이다 |

DB UNIQUE 때문에 중복이 막힌 결과를 모델의 추론 품질로 발표하지 않는다. L3 BLOCKED는 모델이 실제 ERROR 결과를 받아 보류한 경우만 인정한다. 모델 호출 자체가 실패하면 별도의 실패다.
