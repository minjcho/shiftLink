# 10. 합성 데이터·데모 시나리오

> v0.3 구현 문서 · 2026-10-09. 소프트웨어 시험용 합성 데이터이며 실제 설비·안전 절차·현장 성과가 아니다. seed 구현과 실행은 아직 하지 않았다. 아래 기대값은 테스트 runner 전용이며 Agent 입력에 넣지 않는다.

## 1. 고정 식별자와 계정

이 문서는 seed UUID의 기준이다. API 식별자는 UUID이며 CV-03 같은 코드는 표시·검색용이다. 네 계정은 역할·책임 검증용 서버 세션으로 전환한다. 브라우저가 role·owner·assignee를 임의 지정하지 않는다.

| 종류 | UUID | 표시·권한 |
|---|---|---|
| 사업장 | `00000000-0000-4000-8000-000000000001` | SITE-DEMO, 합성 제조사업장 |
| 주 설비 | `00000000-0000-4000-8000-000000000103` | CV-03, 3번 이송 설비, 3호기 |
| 비교 설비 | `00000000-0000-4000-8000-000000000102` | CV-02, 2번 이송 설비, 2호기 |
| 작업자 | `00000000-0000-4000-8000-000000000201` | role=worker, duty=OPERATOR, 최초 제보 |
| 정비 담당자 | `00000000-0000-4000-8000-000000000202` | role=worker, duty=MAINTENANCE, 지정 답변·작업 수행 |
| 출발 책임자 | `00000000-0000-4000-8000-000000000203` | role=supervisor, 최초 owner·작업 승인·인계 생성 |
| 수신 책임자 | `00000000-0000-4000-8000-000000000204` | role=supervisor, 지정 ACK·이후 최종 검증 |
| 출발 교대 발생 | `00000000-0000-4000-8000-000000000301` | SHIFT-20261009-A, 09:00~13:00 KST |
| 수신 교대 발생 | `00000000-0000-4000-8000-000000000302` | SHIFT-20261009-B, 13:00~17:00 KST |

주 설비의 기본 정비 담당자는 `...0202`, 출발/수신 교대 책임자는 각각 `...0203`/`...0204`다. 같은 사업장 내 인접 교대 쌍으로만 인계할 수 있다. 시간은 UTC 저장·Asia/Seoul 표시이며 이 날짜·교대는 데모 설정이다. 실제 서비스 일시에 따라 owner를 몰래 변경하지 않는다.

`POST /demo/session`의 account_key는 작업자 `reporter`, 정비 담당자 `maintainer`, 출발 책임자 `outgoing_supervisor`, 수신 책임자 `incoming_supervisor`로 매핑한다. account_key는 서버 허용 목록이며 실제 role enum은 `worker / supervisor` 두 가지다. OPERATOR/MAINTENANCE는 duty 구분이다.

Incident·Action·Request·Job·evidence ID는 실제 API/DB가 생성한다. 데모 스크립트는 응답 ID를 저장해 다음 명령에 사용한다. 자동 테스트의 독립 DB만 Incident `00000000-0000-4000-8000-000000000401`, Action `00000000-0000-4000-8000-000000000501`을 fixture ID로 예약할 수 있다. 이를 live 생성 결과로 제시하지 않는다.

## 2. 초기 원문 자료

초기 main dataset에는 신규 Incident·질문·주 Action이 없다. `dataset_id=shiftlink-demo`, `dataset_version=0.3.0`으로 참조 데이터를 준비한다. T0는 `2026-10-09T03:00:00Z`(12:00 KST)다. 아래 시각은 합성 관측·작성 시각이고 실제 시험 실행 시각과 구분한다.

| 자료 코드 | UUID | 설비·작성자·시각 | 원문 |
|---|---|---|---|
| LOG-CV03-01 | `00000000-0000-4000-8000-000000000601` | CV-03·작업자·T0-20분 | 3번 이송 설비에서 평소와 다른 소리와 떨림을 느꼈다는 보고를 받음. |
| WO-CV03-14 | `00000000-0000-4000-8000-000000000602` | CV-03·정비 담당·T0-10분 | 초기 점검 완료. |
| WO-CV02-21 | `00000000-0000-4000-8000-000000000603` | CV-02·정비 담당·T0-1일 | 2번 이송 설비의 모의 점검 기록 작성 완료. |

정비표의 ‘완료’는 그 기록의 문장이다. 현재 Incident나 Action 완료로 매핑하지 않는다. WO-CV03-14에 ‘추가 점검 필요’ 같은 정답 힌트를 미리 넣지 않는다. 조회된 원문에 서버 evidence ID를 붙여 출처 유형·설비·작성자·시각·원문 위치를 함께 반환한다.

### SOP-DEMO-01 · version 1 · approved=true

- UUID: `00000000-0000-4000-8000-000000000701`
- 적용: SITE-DEMO / CV-03, CV-02
- 제목: 설비 이상 보고의 기록 확인·인계 절차 — 소프트웨어 시험용
- chunk 경계: 아래 번호별 조항. 문서와 chunk 버전은 함께 기록한다.

원문:

> 이 문서는 ShiftLink 소프트웨어 시험용 가상 절차다. 실제 설비의 조작·정지·재가동·안전을 승인하지 않는다.
>
> 1. 설비 코드, 관찰한 현상, 직접 확인한 내용과 전해 들은 내용을 구분해 기록한다.
> 2. 점검 기록의 범위와 결과가 불명확하면 그 기록을 작성한 담당자에게 범위와 결과를 확인한다. 이미 확인된 내용은 다시 묻지 않는다.
> 3. 후속 확인 작업을 제안할 때 확인할 범위와 제출할 결과 항목을 적고, 실제 수행 전 책임자의 승인을 받는다. 같은 목적의 활성 작업이 있으면 그 작업을 유지한다.
> 4. 데모 확인 작업의 결과에는 확인한 범위, 이전 기록과 달라진 내용, 남은 미확인 사항을 적는다. 물리적 설비 작업 지침을 이 문서에서 만들지 않는다.
> 5. 교대할 때 미해결 사건, 미응답 질문, 남은 작업, 책임자와 작업 담당자를 함께 전달한다. 인수는 문제 해결과 별개다.
> 6. 필요한 질문·작업·결과가 모이고 현재 책임자가 검토 사유를 남긴 뒤 사건을 종료한다. 새 정보가 들어오면 최신 내용으로 다시 판단한다.
> 7. 기록 조회가 실패하거나 근거가 없으면 정상 또는 해결로 추정하지 않는다.

### CASE-DEMO-01 · version 1 · reviewed demo case

- UUID: `00000000-0000-4000-8000-000000000702`
- 설비: CV-02, 시각: T0-7일, 같은 사업장의 해결된 합성 사례
- 제목: 이전 교대의 기록 범위 확인 사례

원문:

> CV-02의 작업자가 평소와 다른 소리를 보고했다. 정비 기록에는 점검 완료라고 적혀 있었다. 작성자 확인 결과 기록은 외관 관찰에 한정됐고 원인 확인 결과는 없었다. 책임자 승인 후 모의 기록 확인 작업을 진행했다. 다음 교대는 미해결 사건과 진행 중 작업을 인수했다. 담당자의 결과 제출과 책임자의 최종 검토 이후 사건을 종료했다. 이는 과거 합성 사례이며 CV-03의 원인·상태를 보여주는 증거가 아니다.

검색 결과에는 `equipment_id`를 항상 표시한다. 다른 설비의 case를 찾았다는 이유로 현재 설비에 같은 원인이 있다고 facts에 저장하지 않는다. 승인되지 않은 SOP나 다른 사업장의 문서는 반환하지 않는다.

## 3. 같은 Incident를 유지하는 Phase 1 진행문

아래 문장은 사람이 화면에서 입력할 합성 시연 대본이다. Agent가 답변이나 결과를 대신 제출하지 않는다. ‘예상’ 열은 oracle이며 모델 입력에서 제외한다. API 명령은 [04_API_CONTRACT.md](04_API_CONTRACT.md), 화면은 [06_UI_SPEC.md](06_UI_SPEC.md)를 따른다.

| 단계·기능 | 실제 입력자 | 입력 원문/조작 | 기대되는 저장 결과 |
|---|---|---|---|
| 1 F1/L1a | 작업자 | “CV-03에서 평소와 다른 소리와 진동을 느꼈어요. 정비팀이 초기 점검을 완료했다고 들었어요.” | 원문 보존·새 Incident·Job; live 조회 후 범위 질문 |
| 2 F1/L1b | 지정 정비 담당자 | “외관만 확인했습니다. 추가 점검 결과는 없습니다.” | 같은 Request의 ANSWERED와 답변 원문; 새 run에서 Action 후보·정식 PROPOSED 1개 |
| 3 F2 | 출발 책임자 | 승인 사유: “제안된 모의 기록 확인 범위와 완료 기준을 확인했습니다.” | 해당 immutable payload 승인 |
| 4 F2 | 같은 정비 담당자 | 승인된 Action의 착수 버튼 | Action IN_PROGRESS |
| 5 F3 | 출발 책임자 → 수신 책임자 | 지정 교대 인계 생성, 수신 책임자가 항목별 현재 내용 확인 후 ACK | owner 이전, 같은 assignee 유지, 사건 미해결 |
| 6 F2 | 같은 정비 담당자 | “데모 기록 확인을 마쳤습니다. 이전 완료 기록은 외관 확인만 뜻했습니다. 이번 모의 확인 범위와 결과를 기록했으며, 제출한 기록에서 추가 미확인 항목은 없습니다. 실제 설비를 조작하거나 안전을 검증한 결과는 아닙니다.” | 작성자·시각이 있는 completion_report, Action COMPLETED, 준비 조건 충족 시 PENDING_VERIFICATION |
| 7 F4 | 수신 책임자/current owner | 검토 사유: “질문 답변, 승인된 범위, 제출 결과와 남은 항목을 확인했습니다. 합성 시나리오의 기록 검토를 종료합니다.” | 최신 버전·근거 검사 후 RESOLVED와 resolution_case 1개 |

Action의 scope·완료 기준 문장을 fixture 정답으로 강제하지 않는다. 의미 기준은 ‘초기 기록 범위와 남은 확인을 다루고, 승인 필요·지정 담당자·제출 결과 조건을 갖춘다’이다. 결과 내용은 실제 승인된 기준에 맞게 사람이 확인해서 입력한다. 기준이 다른데 정해진 대본을 붙여넣어 PASS로 처리하지 않는다.

주 시나리오는 미해결 상태에서 ACK를 먼저 수행하고 결과·검증까지 같은 ID를 유지한다. `snapshot_version=7 → ACK version=8` 숫자는 계약 설명용 예시이며 실제 run이 꼭 같은 숫자를 만들 필요는 없다.

## 5. Phase 2 평가용 변형

필수 L1a/L1b/L2/L3 이후 L4 대조를 권장한다. 초기 입력에 담당자가 작성한 점검 범위·결과가 이미 충분하면 같은 질문을 반복하지 않아야 한다. 이 대조를 실시하지 않았다면 입력별 판단 품질까지 검증됐다고 주장하지 않는다.

표현만 바꾼 holdout 예: “3호기에서 평소와 다른 떨림을 느꼈습니다. 작업표는 완료인데 어떤 항목을 봤는지는 모르겠습니다.” 답변: “눈에 보이는 부분만 확인해 기록했습니다. 그 밖의 확인 결과는 적지 않았습니다.” 개발 입력과 별도로 보관하며 개발 중 기대 출력 튜닝에 쓴 데이터는 holdout으로 세지 않는다.

충분한 입력·표현 변경·다른 근거 조합·반복 실행의 실제 횟수는 결과에 기록한다. 결과가 좋아질 때까지 시도를 삭제하거나 성공한 것만 공개 모수로 선택하지 않는다.

## 6. seed·실행 증거·reset

- seed 입력은 모델 실행 결과가 아니다. `dataset_version`, 문서 버전·해시, seed 시각, 실제 run 시각을 분리한다.
- source 자료와 oracle을 별도 디렉터리/객체로 관리한다. 검색 도구는 oracle을 읽을 수 없어야 한다.
- 실행마다 `dataset_id, trial_id, app commit, mode, model/prompt/tool-schema version`과 실제 ID·도구 결과·최종 DB 상태를 [TEST_RESULTS 양식](../templates/TEST_RESULTS.md)에 연결한다.
- 새 trial은 격리 DB/schema 또는 명시적 dataset 경계에서 시작한다. 실행 중 dataset reset은 차단한다. 종료된 실제 증거를 보존한 뒤 합성 데이터만 재설정한다.
- 미등록 사업장·잘못된 사용자 등 보안 시험 데이터는 별도 테스트 fixture로 만든다. 데모 계정 4개의 권한 의미를 편의상 바꾸지 않는다.

현재 상태: 모든 seed·live·E2E 실행은 **NOT_RUN**. 실제 결과를 채우기 전 이 문서의 기대 경로를 성공 기록으로 인용하지 않는다.
