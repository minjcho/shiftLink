# 06. 화면·사용자 경험 명세

> v0.3 구현 문서 · 2026-10-09. 구현 `NOT_STARTED`, 브라우저 검증 `NOT_RUN`.
> PC 시연과 모바일 너비의 제보 입력을 대상으로 한다. 세 화면의 기능별 패널을 각 기능 담당자가 실제 API와 함께 구현한다.

## 1. 화면 구조와 소유 범위

| 화면 | 경로 제안 | 구현 담당 제안 | 화면이 끝까지 수행할 일 |
|---|---|---|---|
| S-01 제보·미해결 목록 | `/incidents` | F1 재곤 | 설비 선택·원문 접수·실제 ID·목록 재조회 |
| S-02 통합 Incident 상세 | `/incidents/:id` | F1/F2/F4 패널별 | 질문/답변·작업·검증·근거·이력을 한 사건에서 수행 |
| S-03 교대 인수 | `/handovers/:id` | F3 재곤 | 생성·기본 목록·revision 확인·항목별 ACK |

공통 셸·API client·세션·오류 형식·공유 상세 DTO는 F0에서 한 사람이 통합한다. 별도 작업함·대시보드·관리자 제품 화면을 추가하지 않는다. ‘내 확인 요청/작업’은 S-01 필터 또는 S-02 패널로 제공한다. 진단은 상세 화면의 접힌 개발용 영역으로 충분하다.

화면에서 사용할 데이터는 [API 계약](04_API_CONTRACT.md)의 실제 조회 응답이다. 아래 컴포넌트 이름·경로는 구현 예정안이며 현재 파일이 있다는 뜻이 아니다. enum과 상태 전이는 [도메인](03_DOMAIN_MODEL.md)을 따른다.

## 2. 공통 레이아웃·상호작용

상단에 `ShiftLink / 사업장 / 현재 사용자·교대 / 합성 데모 자료`를 표시한다. 허용된 데모 환경에서는 네 계정 전환을 제공하며 서버 세션 결과를 받은 뒤 권한 UI를 갱신한다. 계정 이름 선택만으로 클라이언트 role을 바꾸지 않는다. 세션 전환 시 작성 중인 내용은 보존하거나 명시적으로 정리하고 이전 사용자의 쓰기 요청을 새 세션으로 자동 재전송하지 않는다.

각 화면에는 마지막 성공 조회 시각을 표시한다. 로딩·빈 목록·조회 실패·오래된 캐시를 구분한다. 폴링 중에는 마지막 정상 화면을 유지하고 실패 배지를 붙인다. 편집 중인 입력을 폴링 응답으로 덮어쓰지 않는다. 사건 목록에서 추가로 읽은 페이지 범위는 폴링 때도 유지하며 첫 페이지부터 최신 cursor로 같은 페이지 수를 다시 읽어 전체 성공 시 반영한다. 중간 페이지 조회 실패는 이전 목록·cursor·마지막 성공 시각을 유지한다. 필터 변경은 첫 페이지로 돌아가고 이전 조회 응답을 섞지 않는다.

상태는 텍스트와 색을 함께 사용한다. 사건 해결, 작업 결과 제출, 교대 인수, AI 실행 결과를 서로 다른 줄/배지로 표시한다. ‘인수 완료’ 또는 ‘AI 성공’을 사건 해결로 보이게 하지 않는다.

접근성 최소 기준은 입력 label, 키보드로 조작 가능한 버튼, 오류 위치 연결, 제출 중 상태 안내다. 제보 입력은 좁은 화면에서 가로 스크롤 없이 사용할 수 있게 한다. 모션·차트·음성 UI는 우선 구현 대상이 아니다.

## 3. S-01 제보·미해결 목록 — F1

**관련:** FR-02, AC-F1.1~3. **조회:** `/me`, `/equipment`, `/incidents`.

**입력:** 허용 설비 선택, 제보 원문, 제출 버튼. 예시 문구는 placeholder로만 사용하고 실제 전송 값을 자동 채우지 않는다. 새 사건 연결·병합을 사용자가 선택하게 하는 중간 단계는 없다.

**접수 흐름:**

1. 제출 시 입력 스냅샷과 새 중복 키를 고정하고 버튼을 잠근다.
2. 네트워크 결과가 불확실하면 같은 입력·키로 재전송한다. 내용 수정은 별도 명령과 새 키다.
3. 202 이후 `접수 완료 · 조사 대기`, 실제 Incident ID와 원문을 보여주고 S-02로 이동한다.
4. AI 오류는 ‘제보는 저장됨’과 함께 별도로 보여준다. API 접수 실패와 혼동하지 않는다.

**목록:** 설비, 사건 상태, 현재 owner, 미응답 질문/미완료 작업, 최근 변경을 표시한다. 미해결을 기본 필터로 하고 해결 이력도 조회할 수 있게 한다. 목록 0건은 실제 성공한 빈 응답일 때만 표시한다.

**검증:** 네트워크 오류 후 원문 보존, 중복 클릭 후 동일 ID, 새로고침 후 DB 원문, AI 중지 후 접수 상태를 확인한다. 사용자가 입력한 원문을 AI 요약으로 대체하지 않는다.

## 4. S-02 상세 화면 배치와 패널 경계

```text
CV-03 · Incident ID                       [사건 상태] [업무 버전]
현재 책임자 owner / 교대                  마지막 갱신 시각

원문·추가 기록             AI 조사 참고
작성자·시각·질문 연결      사실·사람 진술 / 가설 / 미확인 / 근거

확인 질문·답변(F1)         작업 제안·승인·수행(F2)
질문 대상·목적·상태        범위·담당자·기한·완료 기준·작업 상태

최종 검증·해결 이력(F4)
준비 조건·사람 결과 검토·해결 또는 반려 사유

교대 인수 요약(F3) / 시간순 업무 이력 / 근거 보기
접힌 실행 진단: 실제 run·모드·도구·오류·버전
```

`IncidentDetailPage`는 F0가 패널 슬롯과 단일 상세 조회를 통합한다. F1은 원문·질문·조사 패널, F2는 작업 패널, F4는 검증/해결 패널, F3는 인수 요약과 링크를 맡는다. 각 담당자는 패널뿐 아니라 대응 API·데이터·검증도 구현한다. 상위 화면을 각자 복제하거나 서로 다른 응답을 합성하지 않는다.

## 5. S-02 질문·답변·조사 패널 — F1

**질문 카드:** 실제 Request ID, `VERIFY_SCOPE|VERIFY_RESULT` 목적, 대상자, 질문 원문, 생성 시각, OPEN/ANSWERED 상태, 관련 근거. 지정 사용자에게만 답변 입력을 노출한다. 답변은 같은 Incident의 `reply_to_request_id`와 최신 버전으로 전송한다.

질문이 없는 상태, 생성 중, 답변 대기, 답변 저장 후 새 조사 중을 분리한다. 답변 뒤에는 새 run이 생긴 사실을 진단에서 확인하되 사용자에게 JSON payload를 요구하지 않는다.

**조사 패널:** 확인 사실과 사람 진술, 가설, 미확인 정보를 구분한다. 근거를 누르면 서버 ID에 해당하는 제목·원문 발췌·출처·버전·설비 범위를 연다. 모의 로그/SOP/사례임을 표시한다. 과거 사례는 현재 사건의 직접 측정 결과로 표현하지 않는다.

분석의 `base_version`이 현재 업무 버전과 다르면 `이전 정보에 대한 분석 · 갱신 필요`를 표시한다. `BLOCKED`와 조회 ERROR를 정상 또는 문제 없음으로 바꾸지 않는다. `review_required=true`이면 분석 갱신과 별도로 후속 검토 필요 배지를 유지한다.

## 6. S-02 작업 패널 — F2

**공통 표시:** 실제 Action ID, 상태, 범위, assignee, 기한, 완료 기준, 근거. AI가 고른 draft는 정식 Action ID와 구분하고 finalizer 확정 전 ‘작업 생성 완료’로 표시하지 않는다.

| Action 상태 | 허용된 사용자 조작 | 필수 표시/제약 |
|---|---|---|
| PROPOSED | 현재 owner supervisor의 승인/반려 | 승인 대상 전체 내용과 필수 사유 |
| APPROVED | 지정 assignee의 착수 | 승인자·시각·승인된 내용, 편집 버튼 없음 |
| IN_PROGRESS | 지정 assignee의 결과 제출 | 결과 원문 필수, 기존 근거 추가 선택 가능 |
| COMPLETED | 결과·최종 검증 상태 조회 | 작업 결과 제출과 사건 해결을 별도 표시 |
| REJECTED | 사유·이력 조회 | 후속 검토 필요, Phase 1 재작업 버튼 없음 |

승인·착수·완료 요청은 Action과 Incident의 버전을 모두 전송한다. 화면에서 숨긴 버튼과 무관하게 서버 권한 검사가 필요하다. 승인 전 착수·직접 완료, 승인 후 내용 변경·재배정 버튼은 만들지 않는다.

결과 제출은 작성자·시각 있는 completion report를 만든다. 추가 근거 선택은 선택사항이다. 성공 후 Action COMPLETED와 실제 Incident 상태를 재조회한다. 조건이 부족한 경우 `작업 결과 제출됨 · 사건 미해결`이며 임의로 최종 검증 대기로 바꾸지 않는다.

## 7. S-02 최종 검증·해결 이력 패널 — F4

현재 owner supervisor에게 검증 조작을 제공한다. `PENDING_VERIFICATION`과 서버가 제공한 준비 조건, 승인된 작업, 제출된 결과, 필수 답변, 근거를 함께 보여준다. 검토 notes를 필수 입력으로 받고 `해결 확인` 또는 `후속 검토로 돌려보내기`를 실행한다.

입력 중 새 버전이 보이면 이전 화면으로 검증하지 못하게 안내한다. 버튼을 비활성화하더라도 서버에서 최신 조건을 다시 확인한다. ACK나 AI 성공만으로 검증을 활성화하지 않는다.

RETURN 또는 승인 반려 후에는 `후속 검토 필요`와 사유를 상단에 고정한다. 완료 Action과 과거 기록은 남겨두며 Phase 1에 해제·재작업 경로가 없음을 설명한다. 성공한 해결로 집계하지 않는다.

RESOLVED 이후에는 최종 확인자·시각·사유·case snapshot과 전체 이력을 조회한다. 추가 정보 입력을 시도했다면 내용을 보존해 신규 제보로 안내한다. 이 기능의 해결 확인은 설비 재가동 승인이나 실제 현장 안전 인증을 뜻하지 않는다.

## 8. S-03 교대 인수 — F3

**생성 동선:** S-01 상단 인계 영역에서 출발 supervisor가 허용된 인접 교대 쌍을 선택해 생성하고 S-03으로 이동한다. 서버가 지정한 선택지만 제공한다. 클라이언트가 대상 사건이나 receiver를 임의로 정하지 않는다.

**머리말:** 출발/수신 교대, 기준 시각, 지정 수신 책임자, 조회 최신성, 인계 ID. **항목:** Incident ID·설비·상태·미응답 질문·남은 Action·현재 owner·유지될 assignee·내용 revision·근거와 상세 링크.

항목별로 `이 내용을 인수했습니다`를 누르면 revision·snapshot token·Incident expected version을 전송한다. 한 항목 성공을 전체 인수 성공으로 표시하지 않는다. ACK 뒤 `사건 책임자: 수신 책임자 / 작업 담당자: 기존 담당자 / 사건: 미해결`을 확인한다.

ACK 자체의 버전 증가로 곧바로 ‘추가 인수 필요’를 띄우지 않는다. 이후 새 정보는 새 revision과 차이를 표시하고 재확인을 요구한다. 이미 보여준 revision은 과거 내용 그대로 조회한다. cutoff 이후 사건은 ‘추가됨’으로 표시하고 새 snapshot에서 확인한다.

DB 목록 조회 실패 시 이전 내용에 실패·갱신 시각을 표시하고 ACK를 막는다. Phase 1 기본 인계는 AI 설명 생성에 의존하지 않는다. 대상 범위를 벗어난 교대·수신자·해결된 사건의 ACK 거부를 정상 성공으로 바꾸지 않는다.

## 9. 역할별 전주기 동선

| 순서 | 세션 | 화면과 동작 | 다음에 확인할 DB 결과 |
|---|---|---|---|
| 1 | 현장 작업자 | S-01 CV-03 제보 → S-02 | 원문·Incident·Job |
| 2 | 정비 담당자 | S-02 자신의 질문에 답변 | 같은 Request의 답변·새 run·주 Action |
| 3 | 출발 책임자 | S-02 범위/담당/완료 기준 승인 | 승인 내용·APPROVED |
| 4 | 정비 담당자 | S-02 착수 | Action/Incident IN_PROGRESS |
| 5 | 출발 책임자 | S-01 인계 생성 → S-03 | 미해결 대상 snapshot |
| 6 | 수신 책임자 | S-03 항목별 ACK | owner 이전·assignee 유지 |
| 7 | 정비 담당자 | S-02 결과 제출 | completion report·COMPLETED·준비 시 검증 대기 |
| 8 | 수신 책임자 | S-02 최종 검증·이력 열기 | RESOLVED·case snapshot |

Phase 1 시연은 실제 응답에서 받은 동일 Incident ID를 계속 사용한다. 네 역할을 표시만 바꾸는 UI mock으로 검증하지 않는다.

## 10. 공통 오류·재시도·상태 문구

| 상황 | 화면 문구와 동작 |
|---|---|
| 202 접수 | `제보 저장됨 · 조사 대기`와 실제 ID |
| 모델 실패 | `AI 조사 실패 · 제보는 저장됨`, 허용된 재시도 안내 |
| 조회 ERROR | `기록 조회 실패 · 아직 확인되지 않음` |
| 질문 대기 | `담당자 답변 대기`, 대상과 질문 ID |
| 버전 충돌 409 | 입력 보존, `새 정보가 있습니다`, 최신 조회·재검토 요구 |
| 오래된 인계 409 | ACK 성공 표시 금지, 최신 revision을 다시 읽고 재확인 |
| 권한 실패 403 | 역할·담당 관계를 확인하도록 안내, 자동 역할 전환 금지 |
| 멱등 키 충돌 409 | 기존 전송과 다른 내용임을 알리고 의도적 새 제출로 구분 |
| 검토 차단 | `후속 검토 필요`, 사유와 기존 이력 |
| 작업 완료 | `작업 결과 제출 완료`와 별도의 Incident 상태 |
| 해결 완료 | `책임자 최종 확인으로 사건 해결`, 확인자·시각 |

재전송과 새 명령을 구분한다. 실패한 요청을 새 버전으로 자동 바꿔 승인·ACK·해결을 재실행하지 않는다. 409 재검토 후 의도적으로 새 명령을 제출할 때 새 키와 최신 버전을 사용한다.

## 11. 진단·검증 기준

접힌 진단 영역에 실제 모드(`live|fake|replay`), 모델, run/Job 상태, 사용한 도구·근거, 오류, 앱/자료/프롬프트 버전을 표시한다. 모르는 식별값은 UNKNOWN으로 남긴다. API 키·세션 비밀·비공개 추론·전체 시스템 프롬프트를 표시하지 않는다. 운영 권한이나 공개 fault-injection 화면을 추가하지 않는다.

| 검증 주체 | 필수 브라우저 확인 | 연결된 서버 시험 |
|---|---|---|
| F1 | 접수·답변 보존, 실제 근거와 질문, 오래된 분석 표시 | T2/T3/T7/T9, L1a/L1b/L3 |
| F2 | 승인 내용, 담당 착수·완료, 반려 차단 | T1/T2/T5/T10 |
| F3 | owner/assignee 구분, 정상/stale/reACK, 추가 사건 표시 | T4/T6/T12 |
| F4 | 준비 조건·버전 충돌·RETURN·해결 snapshot | T1/T5/T6/T8/T10 |
| F5 | 같은 Incident의 네 세션 전주기·새로고침·실제 버전 | T8, 제출 리허설 |

서버 시험 통과와 브라우저 조작 확인은 별도 증거다. 화면 캡처만으로 권한·중복·경합 검증이 끝났다고 기록하지 않는다. 실제 결과는 [시험 계획](07_TEST_PLAN.md), [시험 결과 양식](../templates/TEST_RESULTS.md), [PROGRESS](../PROGRESS.md)에 남긴다.

## 공통 시각 스타일 통합 — 2026-10-09

최신 F1~F4 연결 화면을 기준으로 밝은 회색 배경, 흰 카드, 파란색 포인트, 상단 탐색과 넉넉한 여백을 적용한다. 사건 목록·제보 입력·해결 이력·교대 인수와 상세의 기존 기능/슬롯/명령 흐름은 유지한다. 배너의 기록 남기기는 실제 제보 입력으로 포커스를 옮긴다. 작은 화면에서는 카드와 업무 패널을 한 열로 배치하고 사건 책임자 정보도 함께 표시한다. 계정 변경 시 입력 정리 안내, 상태별 색과 텍스트, 오류·재시도와 최신 조회 시각은 유지한다. 이번 UI 변경의 브라우저 검증은 사용자 요청에 따라 NOT_RUN이다.
