# 01 프로젝트 기획과 목표

v0.3 구현 문서 · 2026-10-09

## 1. 문제와 목표

교대 현장의 “점검 완료” 기록만으로는 실제 확인 범위, 남은 일, 후속 담당자, 해결 확인 여부를 알기 어렵다. ShiftLink는 기록을 조사해 필요한 질문과 작업을 연결하고, 미해결 사건의 책임이 다음 교대로 이어지는 과정을 보존한다.

목표 경험은 한 사건에서 `제보 → 실제 조사와 질문 → 사람 답변 → 작업 제안 → 승인 → 착수 → 미해결 인수 → 결과 → 사람의 최종 확인 → 해결 이력`이 이어지는 것이다. 자료 조회·질문·작업 제안은 AI가 맡고, 권한·상태·책임·업무 반영은 서버와 사람이 확정한다.

## 2. 사용자와 책임

| 사용자 | 실제 수행할 업무 | 끝까지 구분할 책임 |
|---|---|---|
| 현장 작업자 | 제보·자신에게 온 질문 답변 | 현장 원문 제공, 승인 권한 없음 |
| 정비 담당자 | 점검 범위 답변·승인 작업 착수·결과 제출 | Action 수행 assignee |
| 현재 교대 책임자 | 작업 승인·반려·사건 추적·최종 해결 확인 | Incident owner |
| 다음 교대 책임자 | 지정된 미해결 항목을 확인하고 인수 | ACK 후 owner 획득, assignee 유지 |

두 책임자는 supervisor, 작업자·정비 담당자는 worker 역할을 사용하되, 서버의 사건 소유·작업 배정·질문 대상·사업장 검사를 함께 적용한다. 실제 권한 계약은 [도메인](03_DOMAIN_MODEL.md)과 [API](04_API_CONTRACT.md)를 따른다.

## 3. Phase 범위

| Phase | 범위 | 완료 판단 |
|---|---|---|
| 1 필수 전주기 | 동일 사건·주 Action 하나·네 계정·두 교대·세 화면·실제 모델·키워드 검색 | 전주기와 필수 서버 시험, L1a/L1b/L2/L3 live 결과 확보 |
| 2 판단과 예외 강화 | 충분한 입력 대조·holdout, 질문 미응답 교대 시연, 반려 후 다음 Action, 기한 알림 | Phase 1 완료 후 선택한 항목만 구현·회귀 검증 |
| 3 입력·검색 편의 | 확인을 거치는 음성, 실제 누락이 확인된 검색 개선, 작은 화면 편의 | 우선 범위 완료와 제출 여유 확보 후 선택 |
| 공통 제출 | 배포·실제 시연·발표 PDF·Codex 기록·평가 SHA·접수 확인 | 기능 구현과 별도로 제출 인덱스에 실제 값 기록 |

후속 Action은 하나로 제한한다. “외관만 확인했다”는 답변을 과거 작업에 대한 진술로 사용하고, 이를 별도의 첫 Action으로 구현하지 않는다. 승인 반려·검증 RETURN은 Phase 1에서 미해결 보류로 안전하게 끝내며 자동 재승인·재해결하지 않는다.

## 4. 기능별 개발 책임

| ID | 기능 | 초기 담당 | 포함하는 구현 |
|---|---|---|---|
| F0 | 실행 기반·공유 계약 | 재곤 통합, 민재 검토 | 실행·세션·seed·DB·공유 명령/DTO·첫 연결 |
| F1 | 접수·AI 조사·질문과 답변 | 재곤 | 제보 화면, 접수·답변 API, 원문·Request·Job, 도구·최종 확정, 시험 |
| F2 | 작업 제안 확정·승인·착수·결과 | 민재 | Action 패널·명령 API·생성 서비스·승인 불변성·결과 근거·시험 |
| F3 | 교대 인계·인수 | 재곤 | 인계 화면·대상 집합·snapshot·revision·ACK·책임·시험 |
| F4 | 최종 검증·해결 이력 | 민재 | 검증 패널·해결 API·case snapshot·이력 화면·시험 |
| F5 | 전주기·제출 | 공동 | 역할별 실제 연결·실행 근거·배포·리허설·접수 |

초기 배정은 변경할 수 있지만 기능의 화면·API·데이터·시험을 쪼개 개인별 기술 전담으로 돌리지 않는다. 기능 완료를 상대 담당자가 전체 흐름에서 교차 확인한다. [개발 계획](08_BUILD_PLAN.md)의 파일 경계와 통합 순서를 적용한다.

## 5. 스택과 첫 성공 기준

신규 구현은 Vue 3·TypeScript, FastAPI·Pydantic, PostgreSQL·SQLAlchemy·Alembic, 단일 별도 DB worker, OpenAI Responses API, Docker Compose를 기본으로 한다. 이미 동작하는 코드가 확인되면 재사용 근거와 계약 차이를 기록하고 이전한다. 문서 작성 시점에는 앱 코드가 확인되지 않았다.

첫 성공은 화면에서 제보해 Incident·원문·Job을 한 트랜잭션에 저장하고 새로고침 후 같은 원문을 읽는 것이다. 다음으로 실제 모델의 질문·사람 답변·작업 초안을 연결한다. 화면 mock이나 모델 텍스트만으로 기능을 완료 처리하지 않는다.

## 6. 유지할 것과 줄일 것

유지: 원문 보존, 실제 모델 호출, 승인·결과·인수·사람 검증, 권한·중복·최신성 검사, 실패 기록.

축소 순서: Phase 3 전체 → 자동 알림·추가 AI 인계 문장 → 별도 대시보드 → 자료·설비 수. 주 시나리오용 설비 하나와 다른 설비를 잘못 참조하는지 확인할 비교 설비 하나를 사용한다. 기본 인계 목록은 DB로 만든다.

실제 설비 제어·재가동 승인, ERP/정비 시스템 연계, 자동 사건 병합, 다중 병렬 Action, 운영 인증 체계 전체 구축은 이번 필수 범위에 없다.

## 7. 완료 기준과 현재 상태

- 같은 Incident에서 네 역할이 전주기를 한 번 이상 실제 API와 화면으로 완주한다.
- 필수 live 4개 run과 [시험 계획](07_TEST_PLAN.md)의 필수 서버 검증을 실제 실행한다.
- 반려·오류·재시작·오래된 결과에서도 원문과 확정 업무 이력이 남는다.
- 근거 경로·앱 버전·모델·자료 버전·실행 모드를 함께 기록한다.
- 시험·배포·영상·발표가 같은 앱 범위를 설명하고 실제 접수까지 확인한다.

현재 상태는 문서 준비이며 앱·live·통합 시험은 `NOT_RUN`이다. 목표 수치와 실행 결과를 구분한다. 도입 효과는 [파일럿 계획](14_PILOT_AND_VALUE.md)의 측정 가설이며 현재 성과가 아니다.
